# design-harness CLI Implementation Plan

**Goal:** 기존 8단계 명세를 위한 무의존성 Node 20 CLI와 해시 기반 승인을 구현한다.
**Architecture:** Expo와 별개인 `tools/design-harness` 패키지. 동기 파일 검사 코어, 얇은 CLI, 실제 임시 디렉터리 기반 통합 테스트.
**Tech Stack:** Node 20+, ESM, node:fs/crypto/path/test/assert/child_process.
**Spec:** [하네스 설계](../../design-harness.md), 사용자의 check/approve 구현 요청.

## 결정 및 범위

- `check --project <ID> [--root <저장소>] [--json]`, `approve <1..8 또는 단계 ID> --by <이름>`에 같은 프로젝트 옵션을 사용한다. 기본 프로젝트는 bugmap, root는 현재 디렉터리다.
- `work/<ID>`의 공통 파일 및 8단계 산출물의 존재·비어 있음·JSON 구문을 검사한다. 디렉터리 산출물은 실제 비어 있지 않은 파일을 요구한다. 심볼릭 링크는 거부한다.
- 필수 승인 단계: 1, 4, 5, 7, 8. 2, 3, 6은 구조 검사 후 자동 통과. 조건부 승인 정책과 의미·디자인 검증은 후속 범위다.
- `control/approvals.json`은 버전 1의 추가형 이력. 승인자·UTC 시각·UUID·현재 단계까지 파일들의 SHA-256·선행 유효 승인 ID를 저장한다. 파일 추가/삭제/변경 또는 선행 재승인은 하위 승인을 무효화한다. check는 읽기 전용이며 동일 바이트/승인 의존성이 복구되면 기존 승인과 일치한다.
- 승인 쓰기는 잠금과 임시 파일 rename을 사용한다. 잘못된 기록·알 수 없는 인자·경로 탈출·잘못된 JSON은 실패한다. --by는 자기 기입 이름이며 신원 인증이 아니다.
- 구조 통과는 실제 디자인 품질/요구사항 검증 완료의 의미가 아니다. CLI는 파일·검증 산출물을 생성하거나 사람 승인을 대신하지 않는다.
